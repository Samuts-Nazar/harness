## 1. The design on one page

Twelve rules. Everything else in this document follows from them.

1. **One log, one envelope.** Every record (a line of narration, a fact, a character's knowledge, a piece of live state, an attitude, an unsaid remainder, a model-error explanation, a divergence entry) is one row in `record` plus, if it has typed fields, one row in an extension table. Rows are immutable (triggers). Nothing is ever updated or deleted.
2. **Truth, version and feeling are three different records.** A `fact` or `state` record is what is true (or, for `asserted` facts, what someone claimed). A `knowledge` record is one holder's *version* of it, and is the only thing a character's context ever reads. An `attitude` record is a holder's feeling about a version and points to the fact it is about. This is what lets the truth persist while two distorted rumours circulate.
3. **Records are open.** `body` is free text; `tags` and `meta` are open. Panel categories are tags. The typed columns exist only for what code must query (holder, channel, source, observable, ...).
4. **Two times on every record.** `t_from`/`t_to` are in-world time. `logged_world`/`logged_wall` are log time. A record may be written later than it is true (`logged_world > t_from`) under the rules of section 3.3.
5. **Derivation is a link.** `record_link(child, parent, role)` with role `requires` (cascades), `supports` (soft), `about` (reference only) or `replaces`. Links to text carry the word span the record was read from.
6. **Rollback is a tombstone plus a closure.** `rollback(record_id, ...)` marks a record dead. The closure over `requires` links (span-aware for text) is computed and written in one transaction. Everything that reads the log reads through `v_alive`.
7. **"Current" is the latest alive record of a slot.** Live state, attitudes, divergence entries, reputation summaries are registers: `(kind, slot)` keys whose value is the latest alive record. A rolled-back change reverts the register for free.
8. **Perception is computed by code** from presence records and observer state; the extractor proposes only text and typed diffs. The output is `knowledge` rows.
9. **Collectives are entities that hold knowledge.** A town's version is a `knowledge` row whose holder is `town:vergen`. An individual does not inherit it automatically; the individual gets their own row (usually `channel='hearsay'`, `source=<the town>`) when the engine needs it.
10. **Judgments are provenance, not state.** `judgment` is an append-only log of every typed question. A judgment whose answer must stay stable (did news reach place P?) is memoised as a record (`reach`).
11. **Canon is a separate read-only file.** `canon.sqlite` is built once per world; a campaign links into it by `(parent_store='canon', parent id)`. The campaign file holds the divergence ledger.
12. **Isolation is structural.** A prompt builder for a character never receives the campaign database, only a throwaway snapshot holding that character's holder-scoped rows (section 6.2). There is no `fact`, no other holder's knowledge and no hidden state in it, so there is nothing to leak.

```
                 canon.sqlite (read-only, per world, hash-pinned)
                 canon_passage ─ canon_event ─ canon_reaction ─ canon_knower ─ canon_pivot
                        ▲ links (parent_store='canon')
 ────────────────────────┼─────────────────────────────────────────────────────────────
 campaign.sqlite         │
   text units ──requires──► fact / state ──requires──► knowledge ──requires──► attitude
   (player_input,           (truth; narrator-only      (a holder's version;     (feeling; points
    narration, action,       or 'asserted' claims)      persons AND collectives) to fact + version)
    hidden, utterance)            │                           │
        ▲                         └─────requires─────► reach (memo) ─► versions ─► reputation summary
        │  cut (interruption) ─requires─► intent(unsaid)           (supports: soft)
        └─ correction (about, never cascades)       divergence / drift_ruling ─about─► canon
   rollback(record_id)  stale(record_id)  judgment(...)     ← not world state
```

## 2. Stores and files

| What | Where | Why |
|---|---|---|
| Campaign log and all derived records | `campaign.sqlite` (one per campaign; WAL) | The log is the source of truth and the unit of save/restore. |
| Canon | `canon.sqlite` (one per world; opened `mode=ro`; `canon_meta.content_hash` pinned by each campaign) | Immutability enforced by the file system, not by convention. Built once, shared by all campaigns of the world, shippable to a phone as one file. FTS5 and optional embeddings live in it. |
| Per-character memory files (Obsidian-style) | `<campaign>/memory/*.md` | Projection of the log, rewritten after every commit and rollback. Never read back as input to the log. |
| Player panel cache, prefetch results, assistant drafts | outside the log (a `cache` table or memory) | Derived or unsent; keyed by `(max record id, rollback count)`. Drafts are not part of the log until sent (decision). |
| Dev/debug view | queries over everything including dead rows | Not a store. |

A link from a campaign record to a canon record is `(parent_store='canon', parent=<canon record id>)`. SQLite cannot enforce that foreign key across files, so the writer API checks it, and the pinned hash guarantees the ids do not shift.

## 3. The envelope

```sql
CREATE TABLE entity (               -- identities only; everything descriptive is a record
  id        TEXT PRIMARY KEY,       -- 'ragnar', 'marta', 'town:vergen', 'place:heron-taproom'
  type      TEXT NOT NULL CHECK (type IN ('person','collective','place','item','creature')),
  name      TEXT NOT NULL,
  canon_id  TEXT,                   -- id in canon.sqlite if this entity exists in the books
  origin    INTEGER                 -- record that introduced it (entity is dead if that is rolled back)
);

CREATE TABLE record (               -- the envelope: EVERY record in the campaign log
  id            INTEGER PRIMARY KEY AUTOINCREMENT,   -- also the log position
  kind          TEXT NOT NULL,      -- open vocabulary; see the catalogue
  slot          TEXT,               -- "register" key: current value = latest alive record of (kind, slot)
  body          TEXT NOT NULL,      -- the content, free text
  tags          TEXT NOT NULL DEFAULT '[]',   -- JSON array, open vocabulary (panel groups, 'covert', ...)
  meta          TEXT NOT NULL DEFAULT '{}',   -- JSON object, open metadata
  place         TEXT REFERENCES entity(id),
  t_from        INTEGER NOT NULL,   -- IN-WORLD time: when it happened / became true / was learned
  t_to          INTEGER,            -- in-world end (NULL: instant or open-ended)
  t_prec        TEXT NOT NULL DEFAULT 'exact' CHECK (t_prec IN ('exact','hour','day','season','unknown')),
  notability    REAL CHECK (notability BETWEEN 0 AND 1),
  logged_world  INTEGER NOT NULL,   -- LOG time, world clock when written (>= t_from unless scheduled)
  logged_wall   TEXT NOT NULL,      -- LOG time, wall clock (UTC), for the dev view and cost audit
  turn          INTEGER,            -- turn counter at writing
  writer        TEXT NOT NULL CHECK (writer IN ('code','extractor','judgment','player','ingest')),
  writer_ref    TEXT,               -- 'j:<judgment id>' | model id | 'turn:<n>'
  CHECK (t_to IS NULL OR t_to >= t_from)
);
CREATE INDEX idx_record_slot ON record(kind, slot, t_from, id);
CREATE INDEX idx_record_kind ON record(kind, t_from);

CREATE TABLE record_link (          -- derivation and reference edges (child -> parent)
  child        INTEGER NOT NULL REFERENCES record(id),
  parent_store TEXT NOT NULL DEFAULT 'campaign' CHECK (parent_store IN ('campaign','canon')),
  parent       INTEGER NOT NULL,
  role         TEXT NOT NULL CHECK (role IN ('requires','supports','about','replaces')),
  span_from    INTEGER,             -- word range inside the parent's text (1-based, inclusive);
  span_to      INTEGER,             -- only for links to text units
  PRIMARY KEY (child, parent_store, parent, role)
);
CREATE INDEX idx_link_parent ON record_link(parent_store, parent, role);

CREATE TABLE rollback (             -- append-only tombstones; a record is dead iff it has a row here
  record_id  INTEGER PRIMARY KEY REFERENCES record(id),
  root_id    INTEGER NOT NULL,      -- the record whose removal started this cascade
  by_record  INTEGER REFERENCES record(id),   -- the interruption / correction that caused it (NULL: debug)
  reason     TEXT NOT NULL CHECK (reason IN ('interruption','model_error','turn_failed','debug')),
  at_seq     INTEGER NOT NULL       -- max(record.id) when the rollback ran
);

CREATE TABLE stale (                -- alive, but one of several `supports` parents died
  record_id  INTEGER PRIMARY KEY REFERENCES record(id),
  lost_parent INTEGER NOT NULL,
  at_seq     INTEGER NOT NULL
);

CREATE TABLE judgment (             -- provenance of every typed judgment (not world state)
  id        INTEGER PRIMARY KEY AUTOINCREMENT,
  batch     INTEGER NOT NULL,       -- questions about one state share a batch (one Jev call)
  tag       TEXT NOT NULL,          -- 'salience', 'unknown_claim', 'reach', 'symptom', ...
  kind      TEXT NOT NULL CHECK (kind IN ('yes_no','choice','score')),
  question  TEXT NOT NULL,
  options   TEXT,                   -- JSON, for choices
  answer    TEXT NOT NULL,
  p         REAL,                   -- probability of the answer
  backend   TEXT NOT NULL,          -- 'jev-1.13' | 'jev-1.14' | an allowed cheap LLM
  escalated INTEGER NOT NULL DEFAULT 0,   -- 1: Jev p < 0.8, the LLM answer was used
  inputs    TEXT NOT NULL DEFAULT '[]',   -- JSON: record ids the question was built from
  logged_wall TEXT NOT NULL,
  cost_usd  REAL
);
```

### 3.1 Columns that need explaining

* `kind` is an open vocabulary, but the writer API keeps a registry of kinds with their extension table, required links and `writer` values, and rejects anything else. Adding a kind is a code change, not a migration.
* `slot` makes a kind a **register**. The value of a register at in-world time `:T` is the latest alive record with `t_from <= :T`, ordered by `(t_from, id)`. The canonical as-of query (used everywhere, shown with `kind='state'`):

```sql
SELECT r.* FROM v_alive r
WHERE r.kind = 'state' AND r.t_from <= :T
  AND r.id = (SELECT x.id FROM v_alive x WHERE x.kind = r.kind AND x.slot = r.slot
              AND x.t_from <= :T ORDER BY x.t_from DESC, x.id DESC LIMIT 1);
```

  Slot conventions: state `'<subject>|<elem>'`; attitude `'att|<holder>|<knowledge id>'`; presence `'presence|<entity>'`; belief_update `'bel|<knowledge id>'`; membership `'mem|<member>|<collective>'`; divergence `'div|<key>'`; summary `'rep|<subject>|<place>'`, `'gossip|<collective>|<topic>'`.
* `body` is the content for every kind. For a text unit it is the text **delivered when written**; for knowledge it is the holder's version; for a correction it is the player's words verbatim.
* `writer` says who proposed it: `code` (deterministic, including perception), `extractor` (an LLM diff validated by code), `judgment` (Jev or an allowed cheap LLM), `player`, `ingest`. `writer_ref` is `j:<judgment id>`, a model id or `turn:<n>`.
* `place` is an entity id. `notability` is the single 0..1 scalar of the decisions; the *kind* of loudness (violence, scandal, ...) is a tag such as `kind:violence`.
* `t_prec` records how exact `t_from` is; canon events often have only an order.

### 3.2 Link roles

| role | meaning | cascades on rollback? |
|---|---|---|
| `requires` | the child exists only because of the parent (derived from it) | **yes**: parent dead => child dead |
| `supports` | the child summarises several parents | only when **all** its `supports` parents are dead; if some die it is marked `stale` and survives |
| `about` | the child mentions the parent (a correction about a bad output; a drift ruling about canon) | no |
| `replaces` | the child is the regenerated version of the parent | no (informational; the debug view shows the diff) |

`span_from/span_to` (1-based word positions, inclusive) are set on links to text units. They say *which words* the child was read from. A link to a text unit without a span means "the whole text".

The writer API maintains one invariant the database cannot: **`knowledge.about`, `knowledge.source_knowledge`, `attitude.knowledge_id` and `reach.about` each have a matching `requires` link.** A trigger on `record_link` also refuses a `requires` link to a record that is already dead (section 4, R5).

### 3.3 Time rules

* **T1.** `t_from` is when the thing happened, became true, or (for knowledge) was learned. `t_to` is an end if known. A timed effect uses `state_elem.expires_at` instead of a closing record (it lapses by itself).
* **T2.** `logged_world` is the world clock when the row was written; `t_from <= logged_world` always. The future is not in the log. Scheduled things (canon pivots) live in canon; timed effects carry `expires_at`.
* **T3. Back-dating** (`t_from < logged_world`) is legal for records computed lazily about the past: `knowledge`, `reach`, `intent` (tellable, plan), `summary`, `state` written by a symptom or elapsed-time judgment, and `time_passes`. It is **never** legal for text units, the extractor's facts, interruptions or corrections (those are written when they happen).
* **T4. Frozen horizon.** A back-dated record about holder H may not predate H's last *delivered* output unless a yes/no judgment ("does it contradict what H said or did after `t_from`?") answers no. Otherwise it is re-dated to just after that output. This keeps lazy back-filling from contradicting text the player has already read.
* **T5. Memoisation.** A lazy decision that other records depend on is written once as its own record and never recomputed (`reach`). Two NPCs of one town asked at different times inherit the same answer.
* **T6. Materialise before the scene.** Lazy records needed to open a scene are committed in their own transaction *before* the scene's first turn, so rolling back the scene reaches them only through links.
* **T7.** The world clock is `max(t_to of alive time_passes, t_from of alive text units)`; both time modes (turn-based and flowing) write `time_passes` records with `meta.mode`. When the app is in the background nothing is written.

### 3.4 Views

```sql
CREATE VIEW v_alive AS
  SELECT r.* FROM record r
  WHERE NOT EXISTS (SELECT 1 FROM rollback b WHERE b.record_id = r.id);

-- current value of every register ("now"; the as-of form takes :T and :L, see schema.md)
CREATE VIEW v_current AS
  SELECT r.* FROM v_alive r
  WHERE r.slot IS NOT NULL
    AND r.id = (SELECT x.id FROM v_alive x WHERE x.kind = r.kind AND x.slot = r.slot
                ORDER BY x.t_from DESC, x.id DESC LIMIT 1);
```

## 4. Rollback

**R1. Dead means a tombstone.** A record is dead iff it has a row in `rollback`. All reads go through `v_alive`. Nothing is deleted, so the debug view can show the full history with `root_id`, `by_record`, `reason`.

**R2. Closure.** Rolling back a set of seed records kills every record reachable through `requires` links:

```sql
WITH RECURSIVE d(id) AS (
  SELECT value FROM json_each(:seeds)
  UNION
  SELECT l.child FROM record_link l JOIN d ON l.parent = d.id
  WHERE l.role = 'requires' AND l.parent_store = 'campaign')
SELECT id FROM d WHERE id NOT IN (SELECT record_id FROM rollback);
```

The same query without the insert is the dry run (the debug view and the tests use it).

**R3. Text is span-aware.** On an interruption at word `c` of utterance `U`, the seeds are the children of `U` linked with `span_to > c` (or without a span):

```sql
SELECT child FROM record_link
WHERE parent = :U AND parent_store = 'campaign' AND role = 'requires'
  AND (span_to IS NULL OR span_to > :c);
```

Facts read from the delivered words survive; facts read from the cut words die; the extractor does not have to be called again. Where the extractor could not give a span for a record, the record carries no span and dies on any cut (conservative; the engine may re-extract from the kept prefix as the task 4 code does).

**R4. Soft links.** After the closure, repeat until nothing changes: any record whose `supports` parents are all dead is killed (with its own closure); any alive record that lost *some* `supports` parents gets a row in `stale`. A stale record keeps being read; the next context assembly that needs it re-derives it (a new record in the same slot, which supersedes it).

**R5. Guard against resurrection.** The `link_requires_alive` trigger refuses a `requires` link to a dead parent. Lazy jobs (prefetch, spread, off-screen updates) read the log at some position `L`; when they commit they insert their rows in one transaction, and if the guard trips the whole job result is discarded. A rollback therefore cannot be undone by a slow background job finishing afterwards.

**R6. What does not cascade.** `about` and `replaces` links; `player_input` (the player's turn stays when an output is regenerated); `correction` (the explanation must survive the removal of the output it complains about); `interruption` and the `unsaid` intent (they are caused by the cut, not by the cut words: they link to the delivered prefix only); canon.

**R7. Who may roll back.** The engine exposes `rollback(seeds, reason, by)` with a *mode* gate. In normal play only `interruption`, `model_error` and `turn_failed` (an atomic abort of the turn in progress) are accepted. `debug` (any seed, "what if", rewind) is accepted only when the dev view is open. Choices are final.

**R8. Derived caches** (memory files, panel prose, prefetch results) are keyed by `(max record id, count of rollback rows)` and regenerate when the key changes.

**R9. Entities** whose `origin` record died are hidden by `v_entity`, so a character introduced by a removed output does not linger.

**What rollback cannot do.** It cannot un-show text. For an interruption, the delivered prefix stays in the transcript. For a model error the replaced output disappears from the player's view and is kept only in the debug view.

## 5. Record catalogue

Legend. **Writer:** code / extractor (proposal validated by code) / judgment (Jev first, LLM when Jev p < 0.8) / player / ingest. **Read by** names the context assemblies of section 6.

|---|---|---|---|---|

### 5.1 Text units, interruption, presence

```sql
CREATE TABLE text_unit (            -- kinds: player_input, narration, action, hidden, utterance
  id        INTEGER PRIMARY KEY REFERENCES record(id),   -- record.body = text delivered when written
  actor     TEXT REFERENCES entity(id),    -- speaker / acting character
  shown     INTEGER NOT NULL DEFAULT 1,    -- 0: never displayed (narrator's covert channel)
  audience  TEXT NOT NULL DEFAULT '[]',    -- JSON: who perceived it directly; computed by code once, at writing
  generated TEXT NOT NULL                  -- what the model produced (superset of body)
);
CREATE TABLE interruption (         -- kind 'interruption'
  id           INTEGER PRIMARY KEY REFERENCES record(id),
  utterance_id INTEGER NOT NULL REFERENCES text_unit(id),
  after_word   INTEGER NOT NULL CHECK (after_word >= 1),
  mode         TEXT NOT NULL CHECK (mode IN ('live','retro'))
);
CREATE VIEW v_delivered AS          -- how many words of each utterance were really said
  SELECT t.id, t.actor,
         MIN(COALESCE((SELECT MIN(i.after_word) FROM interruption i
                       JOIN v_alive ia ON ia.id = i.id WHERE i.utterance_id = t.id), 1000000),
             LENGTH(TRIM(r.body)) - LENGTH(REPLACE(TRIM(r.body), ' ', '')) + 1) AS delivered_words
  FROM text_unit t JOIN v_alive r ON r.id = t.id WHERE r.kind = 'utterance';
```

* **Output cycle.** The `narration` record is the root of everything the world produced in answer to one player turn: actions, hidden text, NPC utterances, `time_passes`, and every record extracted or derived from them `requires` it (directly or transitively). The `player_input` is its parent. This is what makes "regenerate only the last world output, the player's turn stays" a single rollback of one seed.
* **`audience`** replaces the task 4 `witnesses` list: who perceived the text directly, computed once by code from presence and observer state. NPC "recent conversation" reads it.
* **`hidden`** text is the narrator's covert channel (a poisoner's act, a thought). It is never shown; the extractor reads it; its facts get perception kind `covert` (only the actor).
* **Delivered words.** `record.body` is what was delivered when the row was written; `text_unit.generated` is what the model produced. A live interruption writes the utterance with the delivered prefix as `body` and the rest as an `unsaid` intent. A retroactive interruption leaves the utterance as written and adds an `interruption` record; `v_delivered` gives the number of words really said, and every reader truncates to it.
* **Presence** is a register per entity (`room`, `nearby`, `away`). The task 4 `Scene` object becomes a view of the alive presence records at `:T`, so rollback, as-of queries and lazy perception all work.

### 5.2 `fact`: truth, and claims about it

```sql
CREATE TABLE fact (                 -- kind 'fact': world truth, or a character's assertion about it
  id          INTEGER PRIMARY KEY REFERENCES record(id),   -- record.body = the fact as free text
  status      TEXT NOT NULL CHECK (status IN ('established','asserted')),
  asserted_by TEXT REFERENCES entity(id),
  CHECK ((status = 'asserted') = (asserted_by IS NOT NULL))
);
```

* `established`: world truth. Sources: narration/action/hidden text, canon, world judgments. Read by the narrator and judgments; never placed in an NPC context.
* `asserted`: a character said it (`asserted_by`). Its truth is **not** settled. The narrator sees it labelled as a claim. It becomes established only if a later narration or judgment establishes the same content (a new `established` fact with an `about` link to the claim).
* **Who writes.** The extractor proposes `{content, source segment, word span, notability, place}`. Code decides `status` from the segment kind (narration/action/hidden => established; a character's utterance => asserted), computes perception, and writes the knowledge rows. The extractor is never asked who knows what.
* **Dedupe.** If a speech claim restates an existing fact, a `match_fact` judgment (choice over candidate facts, plus `none`) decides; on a match no new fact is created, only knowledge rows for the listeners (scenario 1, Joss).

### 5.3 `knowledge`: a holder's version

```sql
CREATE TABLE knowledge (            -- kind 'knowledge': one holder's version of something
  id          INTEGER PRIMARY KEY REFERENCES record(id),   -- record.body = the holder's VERSION (may be distorted)
                                                           -- record.t_from = when the holder learned it
  holder      TEXT NOT NULL REFERENCES entity(id),         -- a person OR a collective
  about       INTEGER,            -- the truth record (fact / state / canon) this is a version of; NULL = rumour with no truth record
  about_store TEXT NOT NULL DEFAULT 'campaign' CHECK (about_store IN ('campaign','canon')),
  channel     TEXT NOT NULL CHECK (channel IN
              ('witnessed','heard','overheard','told','hearsay','read','inferred','sensed','innate')),
  source      TEXT REFERENCES entity(id),                  -- who said / told it; may be a collective; NULL = diffuse or direct
  source_knowledge INTEGER REFERENCES knowledge(id),       -- the source's own record: the chain
  hops        INTEGER NOT NULL DEFAULT 0,
  operators   TEXT NOT NULL DEFAULT '[]',  -- distortion operators applied vs. the truth, JSON list
  stance      TEXT NOT NULL DEFAULT 'unjudged',            -- unjudged|firsthand|believes|suspects|doubts|rejects
  confidence  REAL,
  sincerity   TEXT NOT NULL DEFAULT 'unknown' CHECK (sincerity IN ('unknown','sincere','lie','mistaken')),
                                                           -- source's sincerity: narrator/judgment-only, never in a holder's context
  salience    TEXT NOT NULL DEFAULT 'unjudged' CHECK (salience IN ('unjudged','noteworthy','ignored'))
);
CREATE INDEX idx_knowledge_holder ON knowledge(holder);
CREATE INDEX idx_knowledge_about ON knowledge(about_store, about);
CREATE TABLE belief_update (        -- kind 'belief_update', slot 'bel|<knowledge id>'
  id           INTEGER PRIMARY KEY REFERENCES record(id),
  knowledge_id INTEGER NOT NULL REFERENCES knowledge(id),
  stance       TEXT NOT NULL,
  confidence   REAL
);
CREATE TABLE membership (           -- kind 'membership', slot 'mem|<member>|<collective>'
  id         INTEGER PRIMARY KEY REFERENCES record(id),
  member     TEXT NOT NULL REFERENCES entity(id),
  collective TEXT NOT NULL REFERENCES entity(id),
  present    INTEGER NOT NULL DEFAULT 1
);
```

* `holder` is a person or a collective. `body` is the holder's version (already distorted if it was). `t_from` is when it was learned.
* `about` points at the truth record (fact, state, canon record) the version is of, or is NULL for a rumour with no truth record behind it. `operators` lists the named distortion operators (`exaggerate_magnitude`, `add_motive`, `swap_actor`, `lose_mitigating_detail`, `merge_with`, `add_gloss`, ...); a version must be derivable from the truth by those operators (a yes/no judgment checks it), otherwise it is a hallucination.
* **Source chain.** `source` is the immediate source (a person, a collective, or NULL for "they say"); `source_knowledge` points to the source's own record where one exists; `hops` counts. The chain is recovered by following pointers; it is also what the belief function reads.
* `channel`: `witnessed` (saw it), `heard` (loud thing through a wall), `overheard`, `told` (addressed), `hearsay` (diffuse or collective source), `read`, `inferred`, `sensed` (a healer's examination), `innate`.
* `stance`/`confidence` are set once by a judgment when the belief model is decided (today: `unjudged`, so `neutral_belief` still applies); later changes are `belief_update` records. For the **player character** `stance` stays `unjudged` forever: only the player decides what the character believes.
* `sincerity` (`lie`, `mistaken`, ...) is the source's, for the narrator and judgments; it is never rendered into the holder's context.
* `salience` is the holder's verdict on an *observation* (noteworthy / ignored), set when the row is created by the batched salience judgment.
* **Who writes.** Code writes direct perception (`witnessed`, `heard`, `told`, `overheard`) from presence, observer state and notability. Judgments write lazily derived knowledge (spread, versions, hearsay for individuals, canon seeding). The extractor never writes knowledge.
* **No duplicates.** Code does not write a second row for a holder who already has one about the same truth record, unless the new row adds a different source, a stronger channel (hearsay -> witnessed) or a different version. This is why Hubert's and Ragnar's rows are not re-written when Marta shouts (scenario 1, step 6).
* **Collectives.** Their rows are written by the spread judgments. A collective reacts (attitude, reaction judgments) to *its* rows. An individual member gets an own row when needed (`source=<collective>`, `source_knowledge=<the town's row>`), chosen by a `version_heard` judgment among the town's versions. There is no automatic inheritance, so the unknown-claim check cannot be tricked by "everyone in town knows".

### 5.4 `attitude`

```sql
CREATE TABLE attitude (             -- kind 'attitude', slot 'att|<holder>|<knowledge id>'
  id           INTEGER PRIMARY KEY REFERENCES record(id),  -- record.body: short reason, optional
  holder       TEXT NOT NULL REFERENCES entity(id),
  knowledge_id INTEGER NOT NULL REFERENCES knowledge(id),  -- the version the attitude reacts to
  about        INTEGER,           -- the fact/state it is about (= knowledge.about), NULL for pure rumour
  stance       TEXT NOT NULL,     -- from the world's closed attitude vocabulary
  magnitude    REAL NOT NULL CHECK (magnitude BETWEEN 0 AND 1)
);
```

An attitude points to the version it reacts to (`knowledge_id`) and to the fact that version is about (`about`). Direction is a choice from the world's closed vocabulary, magnitude a score (relationship magnitude goes to the LLM directly, as decided). Latest alive record per slot wins; a rolled-back attitude reverts to the previous one. It requires its knowledge record, so an attitude toward something the holder never learned cannot exist.

### 5.5 `state`: live state elements

```sql
CREATE TABLE state_elem (           -- kind 'state', slot '<subject>|<elem>'
  id          INTEGER PRIMARY KEY REFERENCES record(id),   -- record.body: the element in this state, free text
  subject     TEXT NOT NULL REFERENCES entity(id),         -- person, companion, item
  elem        TEXT NOT NULL,      -- identity of the element: 'sword:steel', 'poison:foxglove', 'wound:left-forearm'
  category    TEXT NOT NULL,      -- default panel tag: body|effect|appearance|gear|possession|companion|standing|posture|inner
  present     INTEGER NOT NULL DEFAULT 1,   -- 0: the element has ended (sheathed, healed, removed)
  observable  INTEGER NOT NULL,             -- 1: others in the scene can perceive it
  perceptibility TEXT,            -- optional JSON {"sight":0.9,"examination":0.8}: refines `observable`
  self_aware  TEXT NOT NULL DEFAULT 'known' CHECK (self_aware IN ('known','suspected','unaware')),
  expires_at  INTEGER             -- timed effects: lapses at this in-world time without a new record
);
```

* One register per `(subject, elem)`. A change is a new record in the register (not an "op"): `present=0` ends it (sheathed, healed), `observable` flips between hidden and observable, a rewritten `body` changes its description. **An element persists until a later record changes it**: the drawn sword is read from the register at any later time.
* `category` is the default panel group (`body`, `effect`, `appearance`, `gear`, `possession`, `companion`, `standing`, `posture`, `inner`) and `tags` are open; neither is a fixed attribute sheet. Everything in the decisions' list (wounds ... inner state) fits as elements; nothing is a column.
* `observable`: others in the scene can perceive it. `perceptibility` (optional) refines it: `{"sight":0.9,"examination":0.8}` says a healer's examination can reveal a hidden element. This is the one place the schema goes beyond the binary of the decision; see `schema_gaps.md`, G-3.
* `self_aware`: `known`, `suspected`, `unaware`. The panel and the player assistant show only `known`/`suspected` elements. Hidden causes never appear; their **symptoms** do, because a symptom is its own element (`known`) that `requires` the hidden condition.
* `expires_at`: timed effects lapse without a closing record. Readers test `expires_at > :T`.
* **Perception of state.** Observable elements are perceived (a) when they change, by those present, and (b) when someone enters, by the newcomer (and the newcomer's by the room). Each perception is a `knowledge` row about the state record, with a salience verdict per observer.
* **Writers.** Extractor proposals `{subject, elem, category, present, observable, self_aware, text}`, validated against the register by code (the task 4 `check_change`); scripted changes by code; symptoms and progression by judgment at time advance (one batched call per active hidden condition per advance).

### 5.6 `intent`: unsaid remainders, tellables, plans

```sql
CREATE TABLE intent (               -- kind 'intent'
  id            INTEGER PRIMARY KEY REFERENCES record(id),  -- record.body: what the holder meant to say / do
  holder        TEXT NOT NULL REFERENCES entity(id),
  type          TEXT NOT NULL CHECK (type IN ('unsaid','tellable','plan')),
  audience      TEXT REFERENCES entity(id),
  utterance_id  INTEGER REFERENCES text_unit(id),           -- 'unsaid': the cut utterance
  from_word     INTEGER,                                    -- 'unsaid': first undelivered word
  secrecy       REAL,
  player_salience REAL
);
CREATE TABLE intent_resolution (    -- kind 'intent_resolved'
  id        INTEGER PRIMARY KEY REFERENCES record(id),
  intent_id INTEGER NOT NULL REFERENCES intent(id),
  outcome   TEXT NOT NULL CHECK (outcome IN ('said','done','dropped','expired'))
);
```

* `unsaid`: created by the interruption. `utterance_id` and `from_word` point to the cut text; `body` is the remainder (or the intent behind it). It `requires` the *interruption* record, not the cut utterance, so it survives the removal of what was extracted from the cut words (scenario 3).
* `tellable`: "something I'd tell the player", produced by off-screen updates; same table, `audience` NULL or the player.
* `plan`: a short-term intention derived from what the holder learned (scenario 3, Hubert).
* Private: read only for the owner's context (and the narrator). Resolved by an `intent_resolved` record that `requires` the utterance in which it was said.

### 5.7 Spread: `reach`, versions, `summary`

```sql
CREATE TABLE reach (                -- kind 'reach': memoised "did news of X reach place P"
  id        INTEGER PRIMARY KEY REFERENCES record(id),    -- record.t_from = judged arrival time
  place     TEXT NOT NULL REFERENCES entity(id),
  about     INTEGER NOT NULL REFERENCES record(id),       -- the truth record that travelled
  reached   INTEGER NOT NULL,
  earliest  INTEGER               -- physical lower bound computed by code from the map graph
);
```

Information spread is lazy and has three layers:

1. **Physical bound (code).** From the map graph: the earliest time news could reach place P from the event's place. Stored in `reach.earliest`.
2. **Reach (judgment, memoised).** "Has news of this reached P, given its scale and what has happened since?" (choice: no / one version / several) and "when" (choice relative to the bound). Written once as a `reach` record whose `t_from` is the judged arrival time. This is how world behaviour stays judged per situation while remaining stable (T5).
3. **Versions and people (judgments).** For each circulating version: the carrier chain, operators, and text (an LLM writes the text under the operators; Jev cannot write; a yes/no judgment checks derivability). Then per individual: `version_heard` (choice among the town's versions) and an attitude.

`summary` is a free-text register with `supports` links: a town's talk (`gossip|...`), a reputation (`rep|ragnar|town:vergen`), a relationship summary. A reputation outliving individual stories is a `summary` whose supports are the versions; "fading" is a judgment at meeting time that writes a new record in the register, not a formula.

### 5.8 `correction`: model-error explanations

```sql
CREATE TABLE correction (           -- kind 'correction': a model-error explanation
  id         INTEGER PRIMARY KEY REFERENCES record(id),   -- record.body: the player's words, verbatim
  target     INTEGER NOT NULL REFERENCES record(id),      -- the world output that was wrong (its narration record)
  applies_to TEXT NOT NULL DEFAULT '["narrator","npc","extractor"]'
);
```

Stored per campaign, verbatim, written by the player. `target` is the narration record of the bad output. It is linked `about` the output (never `requires`), so the regeneration's rollback leaves it alive. Later generations read the corrections through retrieval (section 6, narrator/NPC/extractor system prompts): the most recent N plus those whose tags match the current situation, within a token budget.

### 5.9 `divergence` and `drift_ruling`

```sql
CREATE TABLE divergence (           -- kind 'divergence', slot 'div|<key>': the campaign-vs-canon ledger
  id        INTEGER PRIMARY KEY REFERENCES record(id),    -- record.body: what differs, one sentence
  status    TEXT NOT NULL CHECK (status IN ('open','absorbed','reconverged')),
  threads   TEXT NOT NULL DEFAULT '[]',                   -- canon pivots / threads it touches
  magnitude REAL
);
CREATE TABLE drift_ruling (         -- kind 'drift_ruling': narration deviated from canon and was JUSTIFIED
  id           INTEGER PRIMARY KEY REFERENCES record(id),
  output       INTEGER NOT NULL REFERENCES record(id),    -- the narration record
  explained_by INTEGER NOT NULL REFERENCES record(id)     -- the campaign record that justifies it
);
```

See section 7.3.

### 5.10 Judgment log

`judgment` (in `core`) records every typed question: tag, kind, options, answer, probability, backend, whether it escalated from Jev, the input record ids, cost. It is append-only provenance, not world state; records point to it with `writer_ref='j:<id>'`. Several questions about one state share a `batch` (one Jev call).

## 6. Reads: context assembly

### 6.1 Matrix

| Assembly | Reads (all through `v_alive`, as of `:T`) | Never reads |
|---|---|---|
| **NPC context** (holder H) | H's `knowledge` (+ latest `belief_update`); H's own `state` with `self_aware != 'unaware'`; H's latest `attitude`s; H's pending `intent`s; H's `salience='noteworthy'` observations not yet surfaced; text units whose `audience` contains H (delivered words only); H's profile; scene header from `presence`; corrections for `npc` | `fact`, others' `knowledge`, `sincerity`, hidden `state`, `hidden` text, `intent` of others |
| **Unknown-claim check** | exactly the NPC context's knowledge, own state and witnessed lines, plus the candidate line | everything else |
| **Narrator** | all alive `fact` (labelled established / asserted), all `state` of the present characters with `observable` and `self_aware` flags, collectives' versions of recent facts with their operators, open `divergence`s touching present entities, canon retrieval, recent text units (all), corrections for `narrator` | dead rows; draft text |
| **Extractor** | the segments of the turn (each tagged with its kind), current `state` of present characters (for validation), entity ids | facts, knowledge |
| **Judgments** (salience, attitude, reach, version, symptom, drift, ...) | only the records named in the question, built by code; collective judgments read the collective's `knowledge`, never the truth | -- |
| **Player assistant** | the PC's `knowledge`, the PC's `self_aware` state, displayed text units, own corrections | other holders, hidden text, truth |
| **Player panel** | the PC's `state` with `self_aware != 'unaware'`, not expired; prose written from those rows only | hidden state |
| **Memory files** | per entity: knowledge, attitudes, intents, state; wikilinks from `holder`, `source`, `place`, `about`; rewritten after each commit and rollback | -- |
| **Dev view** | everything, including dead rows with `rollback`/`stale`, `judgment`, `meta` | -- |

### 6.2 Isolation as structure, not convention

A prompt builder for a character (or for the player assistant) never receives the campaign database. Trusted code runs the **holder-scoped views** below for `(who, t)` and copies the rows into a throwaway in-memory database (the *snapshot*) that contains six tables and nothing else: `knows`, `own_state`, `attitudes`, `intents`, `heard_text`, `scene`. The NPC prompt, the unknown-claim check and the assistant are built from, and only from, the snapshot. There is no `fact`, no other holder's knowledge, no hidden state and no `sincerity` column in it, so nothing can leak, and the set of rows the character was *given* is by construction the set the check treats as *known*.

(An SQLite authorizer on the live connection was tried first and rejected: SQLite flattens correlated subqueries and then reports no owning view for their reads, so "allow base tables only from inside these views" cannot be enforced. The snapshot needs no such trick.)

```sql
CREATE TEMP TABLE ctx (who TEXT NOT NULL, t INTEGER NOT NULL);

CREATE TEMP VIEW v_knows AS
SELECT k.id, r.body, r.t_from AS learned, k.channel, k.source, s.name AS source_name, k.hops,
       COALESCE((SELECT b.stance FROM belief_update b JOIN record br ON br.id = b.id
                 WHERE b.knowledge_id = k.id AND br.t_from <= ctx.t
                   AND NOT EXISTS (SELECT 1 FROM rollback d WHERE d.record_id = br.id)
                 ORDER BY br.t_from DESC, br.id DESC LIMIT 1), k.stance) AS stance,
       k.salience,
       EXISTS (SELECT 1 FROM record_link l JOIN record sr ON sr.id = l.child
               WHERE l.parent = k.id AND l.role = 'about' AND sr.kind = 'surfaced'
                 AND NOT EXISTS (SELECT 1 FROM rollback d WHERE d.record_id = sr.id)) AS surfaced
FROM ctx, knowledge k JOIN record r ON r.id = k.id LEFT JOIN entity s ON s.id = k.source
WHERE k.holder = ctx.who AND r.t_from <= ctx.t
  AND NOT EXISTS (SELECT 1 FROM rollback d WHERE d.record_id = r.id);

CREATE TEMP VIEW v_own_state AS
SELECT r.id, s.category, s.elem, r.body, r.t_from AS since
FROM ctx, record r JOIN state_elem s ON s.id = r.id
WHERE r.kind = 'state' AND s.subject = ctx.who AND r.t_from <= ctx.t
  AND NOT EXISTS (SELECT 1 FROM rollback d WHERE d.record_id = r.id)
  AND r.id = (SELECT x.id FROM record x WHERE x.kind = 'state' AND x.slot = r.slot AND x.t_from <= ctx.t
              AND NOT EXISTS (SELECT 1 FROM rollback d WHERE d.record_id = x.id)
              ORDER BY x.t_from DESC, x.id DESC LIMIT 1)
  AND s.present = 1 AND (s.expires_at IS NULL OR s.expires_at > ctx.t)
  AND s.self_aware != 'unaware';

CREATE TEMP VIEW v_attitudes AS
SELECT a.id, a.stance, a.magnitude, kr.body AS about_version
FROM ctx, record r JOIN attitude a ON a.id = r.id JOIN record kr ON kr.id = a.knowledge_id
WHERE r.kind = 'attitude' AND a.holder = ctx.who AND r.t_from <= ctx.t
  AND NOT EXISTS (SELECT 1 FROM rollback d WHERE d.record_id = r.id)
  AND r.id = (SELECT x.id FROM record x WHERE x.kind = 'attitude' AND x.slot = r.slot AND x.t_from <= ctx.t
              AND NOT EXISTS (SELECT 1 FROM rollback d WHERE d.record_id = x.id)
              ORDER BY x.t_from DESC, x.id DESC LIMIT 1);

CREATE TEMP VIEW v_intents AS
SELECT i.id, i.type, i.audience, r.body
FROM ctx, intent i JOIN record r ON r.id = i.id
WHERE i.holder = ctx.who AND r.t_from <= ctx.t
  AND NOT EXISTS (SELECT 1 FROM rollback d WHERE d.record_id = r.id)
  AND NOT EXISTS (SELECT 1 FROM intent_resolution x JOIN record xr ON xr.id = x.id
                  WHERE x.intent_id = i.id
                    AND NOT EXISTS (SELECT 1 FROM rollback d WHERE d.record_id = xr.id));

CREATE TEMP VIEW v_heard_text AS
SELECT r.id, r.kind, t.actor, r.body, r.t_from AS at
FROM ctx, text_unit t JOIN record r ON r.id = t.id
WHERE t.shown = 1 AND r.kind IN ('utterance', 'action', 'player_input') AND r.t_from <= ctx.t
  AND ctx.who IN (SELECT value FROM json_each(t.audience))
  AND NOT EXISTS (SELECT 1 FROM rollback d WHERE d.record_id = r.id);

CREATE TEMP VIEW v_scene AS
SELECT p.entity, p.place, p.zone
FROM ctx, record r JOIN presence p ON p.id = r.id
WHERE r.kind = 'presence' AND r.t_from <= ctx.t AND p.zone != 'away'
  AND NOT EXISTS (SELECT 1 FROM rollback d WHERE d.record_id = r.id)
  AND r.id = (SELECT x.id FROM record x WHERE x.kind = 'presence' AND x.slot = r.slot AND x.t_from <= ctx.t
              AND NOT EXISTS (SELECT 1 FROM rollback d WHERE d.record_id = x.id)
              ORDER BY x.t_from DESC, x.id DESC LIMIT 1);
```

### 6.3 The queries

NPC knowledge (the core of the context):

```sql
SELECT r.body, k.channel, src.name AS source, k.hops,
       COALESCE((SELECT b.stance FROM belief_update b JOIN v_alive br ON br.id = b.id
                 WHERE b.knowledge_id = k.id ORDER BY br.t_from DESC, br.id DESC LIMIT 1), k.stance) AS stance
FROM knowledge k JOIN v_alive r ON r.id = k.id LEFT JOIN entity src ON src.id = k.source
WHERE k.holder = :who AND r.t_from <= :T
ORDER BY r.t_from, k.id;
```

Recent conversation (delivered words only):

```sql
SELECT r.id, t.actor, r.kind, r.body FROM text_unit t JOIN v_alive r ON r.id = t.id
WHERE :who IN (SELECT value FROM json_each(t.audience)) AND r.kind IN ('utterance','action','player_input')
ORDER BY r.id DESC LIMIT 10;   -- utterances are truncated to v_delivered.delivered_words in code
```

Player panel (also the assistant's own-state section):

```sql
SELECT s.category, s.elem, r.body
FROM (as-of 'state' at :T) r JOIN state_elem s ON s.id = r.id
WHERE s.subject = :pc AND s.present = 1 AND (s.expires_at IS NULL OR s.expires_at > :T)
  AND s.self_aware != 'unaware';
```

Corrections for the narrator prompt:

```sql
SELECT r.id, r.body FROM correction c JOIN v_alive r ON r.id = c.id
WHERE c.applies_to LIKE '%narrator%' ORDER BY r.id DESC LIMIT :k;
```

## 7. Canon and campaign

### 7.1 Two stores

Canon is `canon.sqlite`: immutable (read-only file, no `rollback` table), too large for any context, reached only through retrieval. The campaign is `campaign.sqlite`: mutable, rollback-able. Canon records use the same `entity` and `record` envelope with `writer='ingest'`. A campaign entity with `canon_id` set instantiates a book character; the campaign keeps its own descriptive records about it.

### 7.2 Structured book ingestion (who, what, how others reacted)

```sql
CREATE TABLE canon_meta (           -- one row; campaigns pin `content_hash`
  world TEXT NOT NULL, ingest_version TEXT NOT NULL, content_hash TEXT NOT NULL,
  built_wall TEXT NOT NULL, extractor_models TEXT NOT NULL    -- JSON list of models used
);
CREATE TABLE canon_source (
  id TEXT PRIMARY KEY, title TEXT NOT NULL, lang TEXT NOT NULL, file_sha256 TEXT NOT NULL
);
CREATE TABLE canon_passage (        -- kind 'canon_passage': raw text chunk, the retrieval unit
  id        INTEGER PRIMARY KEY REFERENCES record(id),   -- record.body = the passage text, original language
  source_id TEXT NOT NULL REFERENCES canon_source(id),
  chapter   TEXT, ord INTEGER NOT NULL,                  -- reading order inside the source
  char_from INTEGER NOT NULL, char_to INTEGER NOT NULL
);
CREATE VIRTUAL TABLE canon_passage_fts USING fts5(text, content='', tokenize='unicode61');
CREATE TABLE canon_embedding (passage_id INTEGER PRIMARY KEY, model TEXT NOT NULL, vec BLOB NOT NULL);

CREATE TABLE canon_event (          -- kind 'canon_event': who / what / how others reacted
  id         INTEGER PRIMARY KEY REFERENCES record(id),  -- record.body = WHAT happened, one or two sentences
  ekind      TEXT NOT NULL,         -- violence|magic|death|crime|miracle|scandal|politics|... (open)
  loudness   REAL NOT NULL CHECK (loudness BETWEEN 0 AND 1),
  order_key  INTEGER NOT NULL,      -- story order; always present
  when_prec  TEXT NOT NULL,         -- exact|day|season|year|unknown (record.t_from may be NULL-ish: see t_prec)
  confidence REAL NOT NULL,         -- extractor's own, 0..1
  review     TEXT NOT NULL DEFAULT 'unreviewed' CHECK (review IN ('unreviewed','ok','fixed','dropped'))
);
CREATE TABLE canon_participant (    -- WHO
  event_id INTEGER NOT NULL REFERENCES canon_event(id),
  entity   TEXT NOT NULL REFERENCES entity(id),
  role     TEXT NOT NULL,           -- actor|target|witness|bystander|beneficiary|victim (open)
  PRIMARY KEY (event_id, entity, role)
);
CREATE TABLE canon_knower (         -- who learned of it and how (seed for campaign knowledge)
  event_id INTEGER NOT NULL REFERENCES canon_event(id),
  entity   TEXT NOT NULL REFERENCES entity(id),   -- person or collective
  channel  TEXT NOT NULL,           -- same vocabulary as knowledge.channel
  source   TEXT, delay_minutes INTEGER,
  PRIMARY KEY (event_id, entity)
);
CREATE TABLE canon_reaction (       -- kind 'canon_reaction': HOW OTHERS REACTED
  id          INTEGER PRIMARY KEY REFERENCES record(id), -- record.body = the reaction, free text
  event_id    INTEGER NOT NULL REFERENCES canon_event(id),
  party       TEXT NOT NULL REFERENCES entity(id),       -- person or collective
  reaction    TEXT NOT NULL REFERENCES canon_vocab(reaction),   -- closed list: Jev can choose, not write
  attitude    TEXT,                 -- stance word from the attitude vocabulary
  delay_minutes INTEGER
);
CREATE TABLE canon_vocab (          -- closed reaction vocabulary per party kind
  party_kind TEXT NOT NULL, reaction TEXT PRIMARY KEY, description TEXT NOT NULL
);
CREATE TABLE canon_evidence (       -- every canon_* record -> the passages it was read from
  record_id INTEGER NOT NULL REFERENCES record(id),
  passage_id INTEGER NOT NULL REFERENCES canon_passage(id),
  quote_from INTEGER, quote_to INTEGER,
  PRIMARY KEY (record_id, passage_id)
);
CREATE TABLE canon_relation (       -- kind 'canon_relation': A to B over story order
  id INTEGER PRIMARY KEY REFERENCES record(id),
  a TEXT NOT NULL, b TEXT NOT NULL, rtype TEXT NOT NULL, from_order INTEGER, to_order INTEGER
);
CREATE TABLE canon_pivot (          -- kind 'canon_pivot': a canon event that is scheduled to happen
  id INTEGER PRIMARY KEY REFERENCES record(id),  -- record.body = the pivot
  event_id INTEGER REFERENCES canon_event(id),
  preconditions TEXT NOT NULL,      -- free text, evaluated by judgment against the divergence ledger
  precondition_entities TEXT NOT NULL DEFAULT '[]'
);
-- kinds without an extension table (envelope only): 'canon_rule' (world rules, magic, law, customs)
```

**Output of the ingestion pass: one JSON object per line** (`canon_ingest.jsonl`; it is derived from the books, so it lives under `data/` and is never committed). One object per event:

```json

 "what": "The alderman of a river town refuses to pay a monster-slayer after the kill.",
 "ekind": "crime|politics|violence|...", "loudness": 0.55,
 "when": {"order": 412, "abs": null, "prec": "unknown"},

         {"entity": "coll:townsfolk", "role": "witness"}],

             {"entity": "coll:guild-of-merchants", "channel": "hearsay", "delay_minutes": 4320}],
 "reactions": [{"party": "coll:townsfolk", "reaction": "side_with_weaker", "attitude": "negative",
                "text": "They shout the alderman down.", "evidence": [{"passage": "p:0098", "quote": [120, 214]}]},
               {"party": "char:alderman", "reaction": "retaliate", "attitude": "negative",
                "text": "He has the slayer's room searched.", "evidence": [{"passage": "p:0099", "quote": null}]}],

```

*(Illustrative: invented to show the shape; not taken from the books.)* Companion line types: `passage` (id, source, chapter, order, char range, text), `entity` (id, type, names/aliases in the book's language, kind of collective), `relation` (a, b, type, from_order, to_order), `pivot` (id, what, event, preconditions in plain text, entities), `rule` (world rules). `reaction` values must come from `canon_vocab` (a closed list per party kind: ruler, guild, church, mob, individual), because Jev can choose from a list but cannot write. `quote` is a character range into the passage, so the original wording is recoverable without being copied around.

**Pipeline** (cheap models only; dev-time quality judging by the Claude Code agent on samples, as decided): (1) chunk the text into passages with ranges; (2) per window of passages, an extractor with a JSON schema proposes events, participants, knowers and reactions; (3) entity resolution against an alias table; (4) merge duplicates across overlapping windows; (5) map free-text reactions to the closed vocabulary with a choice judgment; (6) sample review by the agent -> `review` field; (7) load into `canon.sqlite`, compute `content_hash`, build FTS5 and (optionally) embeddings. Language of the books (Ukrainian) affects chunk size and retrieval quality; `canon_source.lang` is kept per source.

### 7.3 Using canon in a campaign

**Seeding knowledge.** When a canon-backed entity first matters (promotion to persistent agent, or first scene), the engine materialises `knowledge` rows from `canon_knower`: `about_store='canon'`, `about=<canon event>`, `channel` from canon, `t_from` = the canon time (negative minutes before the campaign epoch, or the order-derived estimate with `t_prec='unknown'`), `logged_world` = now. This replaces the task 4 placeholder where canon knowers were passed in by the caller.

**Retrieval.** Typed lookup first (entities in the scene, event kinds, order range -> `canon_event`, `canon_reaction`), then FTS5 / embeddings over `canon_passage` for text. Canon reaches narration and judgments only through this path.

**The drift check** (a narrated output contradicts canon):

1. A judgment flags that the output contradicts retrieved canon records (`canon_event`, `canon_relation`, `canon_rule`).
2. Code queries the campaign store for explanations: open `divergence` records and alive campaign records that mention the entities involved, ranked by recency and by `about` links to the same canon records.
3. A yes/no judgment per candidate: "does record X explain this deviation?" Yes => **justified drift**: write a `drift_ruling` (`output`, `explained_by`, `about` link to the canon record) and, if the deviation is itself new and lasting, a `divergence` entry. No candidate => **hallucination**: nothing is written to the campaign; the output is regenerated (counted in the dev log); after the retry limit a hedged output is used.
4. Rolling back the output kills its `drift_ruling` (requires), and with `supports` links, any ledger entry that only it supported.

**Divergence ledger.** Short, always retrievable: each entry has `body` (what differs), `since` (`t_from`), `status` (open / absorbed / reconverged; a new record in the register `div|<key>`), `threads` (canon pivots and events it touches), `magnitude`, and `about` links to the canon records it deviates from. It `requires` the campaign record that caused it. It is shown to the narrator when it touches present entities, and to the reaction judgments.

**Canon pull proportional to the deviation.** The schema supplies the inputs: `divergence.magnitude`, `threads`, and `canon_pivot.preconditions` (plain text). On a time advance, the pivots whose `precondition_entities` intersect open divergences are re-judged ("do the preconditions still hold?", "is the outcome changed?"). Which policy applies (strong / weak / none pull) is not a schema matter and is not decided; the placeholder is "retrieve only".

**Collective reactions** (A3) run on the collective's `knowledge` row, not on the truth: the town's `attitude` (scenario 2) requires the town's version.

## 10. What this design adds that the decisions do not say

(Details and the cases where the decisions cannot be satisfied cleanly are in `schema_gaps.md`.)

1. NPC speech yields **asserted** facts, not established ones (truth stays open until narrated).
2. The narrator needs a **covert output channel** (`hidden`) for acts the player must not see.
3. `supports` links (soft cascade, `stale`) in addition to hard `requires`.
4. `perceptibility` on state (per-channel refinement of observable/hidden).
5. Extractor proposals carry **word spans**; interruption rolls back exactly.
6. Canon in a separate read-only file, pinned by hash.
7. Spread = physical bound in code + judged arrival, memoised (not a fixed formula).
8. Back-dating guard (frozen horizon, T4) and the resurrection guard (R5).
